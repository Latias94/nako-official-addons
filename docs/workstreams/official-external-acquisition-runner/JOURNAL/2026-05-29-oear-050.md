# OEAR-050 Journal

Date: 2026-05-29
Task: OEAR-050 - First Real Runner Adapter Decision
Status: Complete

## Decision

Choose Transmission as the first production adapter candidate, but do not start
implementation in this lane until the host-to-runner materialization contract
exists.

The runner sidecar currently receives only host-owned opaque references. That
is the correct security boundary, but a real adapter cannot enqueue a torrent
from an opaque selected-link or intake-candidate reference unless Nako exposes a
controlled way to materialize the approved link into the sidecar. That
materialization step must be designed before any real downloader adapter.

## Comparison

Transmission is the best first adapter candidate because its RPC model gives a
stable torrent hash on add and duplicate outcomes. That maps cleanly to Nako's
host idempotency and runner job reference model: the sidecar can use
`transmission:<hash_string>` as `runner_job_ref`, query by hash, and stop or
resume by hash without depending on unstable numeric ids.

qBittorrent remains a strong second adapter. Its WebUI API is broad and mature,
with add/list/pause/resume/delete surfaces, categories, tags, and WebUI
authentication. The main reason not to choose it first is idempotency: the add
endpoint is status-code oriented, so the sidecar needs a more careful hash
discovery policy across WebUI API versions before it can report a stable
runner ref without races.

aria2 is attractive as a generic JSON-RPC runner because it covers HTTP,
magnet, torrent, and more. It is not the first adapter because its token/RPC
surface is easier to leak in logs, its GID lifecycle is weaker as an audit
anchor than a torrent hash, and its broad protocol support increases the
initial policy surface.

A plain HTTP downloader is safest from a torrent-control perspective, but it
would force this lane into host file placement, storage quotas, cleanup, resume,
and managed-import boundaries. It also does not solve magnet or cloud-drive
links, so it should be a separate storage/import workstream rather than the
first External Acquisition Runner adapter.

## Required Follow-Up

- Define host-owned selected-link/intake-candidate materialization for runner
  sidecars, including authorization, expiry, audit, and redaction.
- Add a `RunnerAdapter` boundary in the sidecar with `enqueue`, `cancel`,
  `pause`, `resume`, and `query_status`.
- Add a Transmission profile config schema for endpoint, auth secret refs, TLS
  policy, download directory, labels, paused-on-add default, and optional ratio
  policy.
- Build a fake Transmission RPC server test harness that covers add, duplicate,
  status, stop, resume, remove, auth/session behavior, and safe error mapping.
- Keep `runner_job_ref` stable and opaque; for Transmission use
  `transmission:<hash_string>`.
